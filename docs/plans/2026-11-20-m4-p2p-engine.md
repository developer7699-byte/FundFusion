# M4 — P2P Engine Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The platform quotes one price, broadcasts an order to every eligible
merchant at once, and the first to accept wins atomically — with the money
moving only through balanced journals and never on a timeout.

**Architecture:** A `P2pModule` on the M1 ledger. Rates sit behind a provider
interface with a deviation bound that fails closed. Quotes store an immutable
snapshot. Acceptance is one transaction holding two row locks. Settlement is a
single journal. Nothing here touches the chain — the ledger supplies balances,
and how USDT arrived is M3's concern.

**Tech Stack:** NestJS 11 · Drizzle ORM · PostgreSQL 17 · decimal.js

**Spec:** `docs/PRD.md` — M4 row of §14. Engine §6.1–6.11, rates §7,
definition of done §15 items 1–4.

## Global Constraints

- **The snapshot is law.** An order settles at its quoted rate however far the
  market has moved. No historical order is ever recomputed at a current rate —
  not for a receipt, not for a report, not for a dispute. (§7)
- **A timeout may return funds to where they started. It may never advance
  them to someone's benefit.** Receiver silence escalates to `DISPUTED`, never
  to release. Escrow that pays out on silence gets farmed within weeks. (§6.9)
- **Whoever receives the rupees confirms them.** A payer's UTR alone never
  releases escrow — a fabricated reference would drain the system. (§6.8)
- Merchant eligibility is a **USDT** check, never a rupee one: the platform
  holds no rupees, so a rupee balance is self-declared and unenforceable. (§6.5)
- Bond exactly the obligation. **The buffer stays unreserved.** (§6.5)
- The platform's cut comes from an asset it custodies. On sell-side, never
  credit the merchant the full quantity. (§6.3)
- Broadcast is published from **one place at one instant** for all eligible
  merchants. Looping per merchant builds a systematic advantage for whoever
  sits earliest in the loop, and under first-accept-wins that decides who
  earns. Log broadcast and accept timestamps from day one — the first fairness
  complaint is unanswerable without them. (§11)
- All money rules from M1 hold. Balances stay derived; every movement is a
  balanced journal with an `Idempotency-Key`.
- Commit messages: one line, `feat(context): message`, **no** `Co-Authored-By`.

## Review Focus

1. **A quote that expired between confirm and accept** is still honoured,
   letting a merchant pick off stale favourable prices. → Task 4.
2. **Eligibility checked before the row lock** lets two orders consume the same
   merchant balance. → Task 4.
3. **A rate feed spike** of ₹1,000 promises ₹97,000 on a 100 USDT sell because
   no deviation bound rejected it. → Task 1.
4. **A timeout advances an order** to COMPLETED or releases escrow, rather than
   returning funds or escalating to DISPUTED. → Task 6.
5. **Rounding on the derived side** leaves the settlement journal unbalanced by
   a sub-paisa residue that never reaches the ROUNDING account. → Task 5.

- [ ] **Step 2: Run to verify it fails**
- [ ] **Step 3: Implement the six-step transaction from §6.7**

In order, inside one transaction: lock the order row; assert
`AWAITING_MERCHANT` and quote unexpired; assert merchant active and capable;
lock the merchant wallet and **re-check eligibility inside that lock**; insert
the assignment against a `UNIQUE` on `order_id`; post the lock-or-bond journal
and move to `ACCEPTED`. Losers get HTTP 409 `ORDER_ALREADY_ASSIGNED`.

it. A concurrency test that has never failed proves nothing.

- **Five merchants accepting simultaneously produce exactly one winner and
  four `ORDER_ALREADY_ASSIGNED` responses** (PRD §15 item 4).
- Sell-side and buy-side math are exact to the PRD's worked examples
  (§15 items 1–2).
- Collateral eligibility is enforced and only the exact obligation is bonded
  (§15 item 3).
