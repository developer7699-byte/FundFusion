# M5 — disputes, penalties, admin surfaces, reconciliation

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every dispute outcome in PRD §6.10 exercised against a real ledger, with the admin surface to reach them and the reconciliation job that catches what they miss.

**Architecture:** A dispute never moves money by itself. It records that an
order stopped, and an admin's resolution posts exactly one compensating
journal — the same discipline as settlement, because a dispute is settlement
decided by a person instead of by a confirmation. The four outcomes are a
closed list in code, not a free-text field.

**Tech Stack:** NestJS 11, Drizzle, PostgreSQL 16, decimal.js, @nestjs/schedule.

**Spec:** [`docs/PRD.md`](../PRD.md) — §6.10 (disputes), §6.11 (abandonment), §9.2 and §9.4 (admin), §13.1 (reconciliation), §14 (M5).

## Global Constraints

- The ledger is the only truth. No code writes a balance column; an admin correction is a compensating journal like any other movement (PRD §5 rule 1).
- Every money operation is atomic, idempotent and auditable, and carries an `Idempotency-Key` (PRD §5 rule 2).
- USDT is `NUMERIC(38,18)`; money crosses the boundary as **strings** and is computed with decimal.js. A JavaScript `number` never holds money (PRD §5 rule 3).
- Never mock PostgreSQL in a ledger or matching test — the behaviour under test is the database's row locking (PRD §5 rule 4).
- Every privileged action carries an actor and a typed reason, stored. The audit log is append-only (PRD §9.4).
- **No admin may edit a balance directly** (PRD §9.4).
- SUPPORT reads everything and moves no money; only SUPER_ADMIN resolves a dispute (PRD §9.2).
- **A merchant is never penalised for a customer's abandonment** (PRD §6.10).
- **Full forfeiture is never used** — a merchant whose bank had a genuine outage would lose their whole bond, word would spread, and merchant supply would dry up (PRD §6.10).
- Commits: one line, conventional-commit shaped, no `Co-Authored-By` (CLAUDE.md).

## Review Focus

1. **A dispute resolved twice**, posting the journal twice and paying out double. The resolution is the single most dangerous write in the system, and unlike settlement it is triggered by a person who may double-click. Owned by Task 3.
2. **A penalty drawn where no bond exists.** §6.11 says a buying customer cannot post a bond, so `REFUND_WITH_PENALTY` has nothing to draw from on a buy — it must refuse, not post a debit that drives a balance negative. Owned by Task 5.
3. **A split whose parts do not sum to the escrow**, leaving dust stranded in `LOCKED` forever or overdrawing it. Owned by Task 4.
4. **A SUPPORT account resolving a dispute.** The role exists precisely to separate looking from moving money, and a dispute resolution is the largest discretionary movement in the product. Owned by Tasks 3 and 7.
5. **Reconciliation drift that nothing reports.** The job is the one check whose two sides are independent, and a scheduled job that fails silently is indistinguishable from a clean run (PRD §13.3). Owned by Task 8.

- Produces: `ResolutionService.resolve(disputeId, adminId, decision, idempotencyKey)` where
  `decision = { outcome: 'RELEASE' | 'REFUND' | 'SPLIT' | 'REFUND_WITH_PENALTY', reason: string, counterpartyAmount?: string }`.

§6.10's list is written from the sell side. Stated so it holds on both:
**RELEASE** pays the escrow to the counterparty as a normal settlement would
— the payer did pay. **REFUND** returns it to whoever posted it — the payer
did not. Both release any bond. Tasks 4 and 5 add `SPLIT` and
`REFUND_WITH_PENALTY`.

## M5 is done when

- All four §6.10 outcomes have been exercised against a real ledger, and recorded.
- A penalty never exceeds the bond, and never applies where no bond exists.
- A merchant is never penalised for a customer's abandonment.
- Repeated defaults pause a desk, and the engine refuses a paused desk.
- SUPPORT can read every admin surface and resolve nothing.
- Reconciliation runs on a schedule and says so loudly when it drifts.
- Reconciliation is clean after every dispute outcome.
- `lint`, `typecheck`, `test`, `test:e2e` and `build` all exit 0.
