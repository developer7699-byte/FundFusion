# M4.5 — the thin end-to-end spine

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A full sell and a full buy complete on BSC testnet, through HTTP, driven from a browser.

**Architecture:** The engine and the wallet are built and tested; nothing can
reach them. This plan adds the HTTP surface over them, the one-instant
broadcast PRD §11 requires, and the **thinnest** customer and merchant path
that can complete an order. The existing prototype screens stay untouched and
keep pointing at the in-memory prototype API — rewiring 22,000 lines of
prototype UI is M6, and the shapes differ (immutable snapshots, idempotency
keys, an authenticator gate) enough that rewiring now would be a rewrite.

**Tech Stack:** NestJS 11, `@nestjs/websockets` + socket.io, React 19 + Vite,
TanStack Query, supertest, vitest.

**Spec:** [`docs/PRD.md`](../PRD.md) — §6 (the engine), §8 (wallet), §9.1
(identity), §11 (real-time), §14 (M4.5's done condition).

## Global Constraints

- Money crosses the application boundary as **strings**. A JavaScript `number` never holds money (PRD §5.1).
- Every money mutation requires an `Idempotency-Key` header (PRD §5 rule 2).
- Server-side calculation is absolute. Client values are display hints and are never trusted at confirmation (PRD §13.5).
- Moving money requires a verified email **and** an enrolled authenticator (PRD §9.1). `MoneyGateGuard` is the only place that decides this.
- Broadcast is published **from one place at one instant** for all eligible merchants. Looping per merchant builds a systematic advantage for whoever sits earliest in the loop (PRD §11).
- Commit messages: one line, conventional-commit shaped, never a `Co-Authored-By` trailer (CLAUDE.md).
- Out of v1 scope and not to be added: gift cards, game top-ups, utilities, UPI scan-and-pay, verification tiers, staking (PRD §3).

## Review Focus

1. **A merchant accepting their own order.** `AssignmentService.accept` never compares the merchant to `order.customerId`, and PRD §9.1 records that the one-phone-one-account rule that discouraged this is gone (q38). A browser makes it one click. Owned by Task 3.
2. **A stale merchant feed.** An order already assigned, or past its search window, must not appear in the feed — a merchant who accepts one gets a 409 for something the screen told them was available. Owned by Task 3.
3. **A money route with no `Idempotency-Key`, or a replayed one under a different body.** The header is the only thing standing between a retry and a second order. Owned by Task 1.
4. **An unauthenticated socket subscribing to the merchant feed.** Order flow is commercially sensitive and the feed is the whole book. Owned by Task 5.
5. **A quote confirmed after its TTL, or an order accepted after its search window.** Both are already enforced in services; the HTTP layer must surface them as refusals a screen can show, not 500s. Owned by Task 4.

### Task 5: The broadcast

**Files:**
- Create: `api/src/p2p/p2p.gateway.ts`, `p2p.gateway.spec.ts`
- Modify: `api/src/p2p/order.service.ts` (emit at the instant it records), `api/src/p2p/p2p.module.ts`, `api/package.json`

**Interfaces:**
- Produces: `OrderBroadcaster` — an interface with `broadcast(order: FeedOrder): void`, implemented by `P2pGateway`. `OrderService` takes it as an optional constructor dependency so every existing unit test keeps constructing without one.

- [ ] **Step 1: Add `@nestjs/websockets`, `@nestjs/platform-socket.io` and `socket.io`**

- [ ] **Step 2: Write the failing tests**

```ts
// PRD §11 — the fairness property, and the reason it is not a loop.
it('publishes one event for all merchants, not one per merchant', ...)
it('refuses a socket with no valid access token', ...)            // Review Focus #4
it('emits when an order reaches AWAITING_MERCHANT', ...)
it('emits nothing when confirmation is a replay', ...)            // the second call broadcasts nothing
```

- [ ] **Step 3: Run them and watch them fail**

- [ ] **Step 4: Implement**

The gateway authenticates on connection from `handshake.auth.token` using the
same secret `V1AuthGuard` uses, joins every authenticated socket to one room,
and `broadcast()` is a single `server.to('merchants').emit('order.broadcast', …)`
— one call, one instant, no per-merchant iteration.

A single instance needs no Redis adapter; PRD §11's Redis pub/sub is what makes
this correct across *several* instances, and is a config addition at that point.
Record that in the file's doc comment so nobody reads its absence as an oversight.

- [ ] **Step 5: Run them and watch them pass**

- [ ] **Step 6: Commit** — `feat(p2p): broadcast new orders to every merchant at once`

## M4.5 is done when

- A full sell and a full buy complete on testnet, driven from a browser.
- A merchant cannot accept their own order, and is never shown one.
- Every money route requires an `Idempotency-Key`, and a replay returns the first result.
- One broadcast reaches every merchant at one instant, over an authenticated socket.
- Reconciliation stays clean after both orders.
- `lint`, `typecheck`, `test`, `test:e2e` and `build` all exit 0.
