# PRD — Mobile Test Runner with Reporting (Prototype)

**Status:** Draft 1 · **Date:** 2026-10-22 · **Owner:** sriram@pentafox.in
**Source:** Derived from the grilling session (see `grilling.md`, rounds 1–4).

---

## 1. Summary

A local command-line tool that runs an Appium test suite against an Android app
and produces a detailed, accurate HTML report for each run. The app under test is
a real Android trading app. The tool is the seed of a future commercial SaaS for
test reporting and flaky-test triage.

The tool does not drive the app itself. It wraps the user's existing test command,
runs it, and reads the results. This keeps it independent of the test engine, so a
web engine (Playwright) can be added later with no change to the core.

---

## 2. Problem and context

- The team runs no automated UI tests today. This is a greenfield build.
- The team wants to run mobile tests and see a clear, detailed report with analytics.
- Existing runners report poorly and handle flaky tests badly.
- The long-term goal is a commercial SaaS. The near-term goal is a working prototype.

---

## 3. Goals and non-goals

### Goals (prototype)
- Run a real Appium suite end to end against the Android trading app.
- Produce an accurate per-run HTML report with per-test detail.
- Store every run so trends and flaky detection can be added later.
- Stay engine-agnostic so Playwright (web) slots in later.

### Non-goals (prototype)
- No flaky detection yet. (Design the data for it; do not build it.)
- No reruns yet. Run once.
- No live web dashboard yet. (Static HTML only.)
- No multi-user, auth, hosting, or billing yet.
- No test authoring UI. Developers write the test code.
- No web (Playwright) target yet.

---

## 4. Users

- **Primary author:** a developer who writes Appium test code.
- **Primary reader:** the same developer (and later, teammates) reading the report.
- Later SaaS users: QA and dev teams at other companies.

---

## 5. Scope — MVP

### 5.1 Functional requirements

1. **Config file.** The tool reads a small config file (JSON or YAML) in the
   project. It holds:
   - the test command to run,
   - the folder where the run writes JUnit XML results,
   - the folder where tests write screenshots and logs,
   - the target device or emulator.
2. **Run.** The tool runs the configured test command as a child process. It
   captures exit code, stdout, and stderr. It runs the suite once.
3. **Parse.** After the run, the tool parses the JUnit XML results into a run
   record: per-test name, status (pass/fail/skip), duration, and error message.
4. **Collect artifacts.** The tool scans the artifacts folder and links each
   screenshot or log file to its test by an agreed naming or folder convention.
   The tool does not take screenshots itself; the test code saves them on failure.
5. **Store.** The tool writes the run and its test results to a local SQLite file.
   The schema allows many results per test, so reruns and flaky detection add
   cleanly later.
6. **Report.** The tool writes a static HTML report file for the run. It shows:
   - run summary (total, passed, failed, skipped, duration),
   - a per-test table (name, status, duration, error),
   - links to each test's screenshot and log.

### 5.2 Target environment

- **Android emulator**, pending verification (see Risks). The trading app must be
  installed and confirmed to open on the emulator before any test is written.
- **App under test:** the real Android trading app.
- **Login:** username, password, and a **fixed static OTP** in a test or staging
  build. This keeps login deterministic.

### 5.3 First test suite

- Login, then land on the dashboard.
- A few read-only flows (for example portfolio and watchlist).
- **One test with a deliberately wrong assertion.** This is the accuracy check:
  the report must show exactly one failure and all else passing.

## 6. Architecture

```
config file ──▶ Runner ──▶ (child process: user's Appium test command)
                   │
                   ├─▶ JUnit XML  ──▶ Parser ──▶ run record
                   ├─▶ artifacts folder ──▶ Collector ──▶ linked files
                   │
                   ▼
                SQLite (runs, tests, results, artifacts)
                   │
                   ▼
             HTML report writer ──▶ report-<timestamp>.html
```

- **Language:** TypeScript on Node.
- **Key principle:** the tool wraps a command and reads files. It never calls the
  Appium API. The test engine is replaceable; only the command and the results
  format matter.
- **Results format:** JUnit XML first (universal). Allure can follow later for
  native screenshot and step attachments.

---

## 7. Data model (SQLite, rerun-ready)

- `runs` — id, started_at, finished_at, command, exit_code, summary counts.
- `tests` — id, run_id, suite, name, status, duration_ms, error.
- `artifacts` — id, test_id, type (screenshot/log), path.

A test belongs to a run, so the same test name across many runs produces many
`tests` rows. This is what later lets the tool compute flakiness across runs with
no schema change.

---

## 8. Success criteria (prototype is "done")

1. One command runs the trading-app suite on the target environment end to end.
2. The tool writes an HTML report that matches reality: it shows the one seeded
   failure and marks every other test as passed.
3. Every test's screenshot or log (when present) is linked in the report.
4. The run is stored in SQLite and can be read back.

---

## 9. Risks and mitigations

| Risk | Impact | Mitigation |
|------|--------|-----------|
| **Trading app blocks emulators** (root/emulator detection) | Breaks the emulator plan | Verify the APK opens on an emulator before building. If blocked, switch to a real device or a device cloud (BrowserStack, Sauce Labs). |
| **Automating write/trade actions on production** | Real orders, real money | First suite is read-only. Gate any write/trade step behind an explicit opt-in flag. Use a dedicated test account and smallest/cancellable orders. |
| **JUnit XML has no attachments** | Screenshots not embedded | Collect artifact files from a known folder and link them. Add Allure later if native attachments are wanted. |
| **Static OTP is really a real SMS OTP** | First login test cannot automate | Confirm the OTP is a fixed constant in a test/staging build. |
| **Crowded market** (Trunk, BuildPulse, Currents, Datadog CI do ingest-only flaky dashboards) | Weak differentiation for SaaS | Defend the run + report + mobile/trading-app angle, not generic ingest. |

---

## 10. Pre-build action items

1. Install the trading-app APK on an Android emulator and confirm it opens.
2. Get a staging build with the fixed static OTP and a dedicated test account.
3. Stand up Appium and the Android SDK and emulator locally.

---

## 11. Roadmap (after MVP)

1. Reruns, then flaky-test detection (uses the existing SQLite data).
2. Cross-run trends: pass rate and duration over time.
3. Live web dashboard (replaces static HTML).
4. Web target via Playwright (a second command, same core).
5. SaaS: multi-user, auth, hosting, billing.
